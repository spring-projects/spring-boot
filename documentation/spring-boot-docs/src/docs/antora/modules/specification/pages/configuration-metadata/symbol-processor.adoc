[[appendix.configuration-metadata.symbol-processor]]
= Generating Metadata for Kotlin by Using the Symbol Processor

Kotlin code can be processed by the Java annotation processor described in xref:specification:configuration-metadata/annotation-processor.adoc[] through kapt.
As kapt is in maintenance mode, the `spring-boot-configuration-symbol-processor` jar provides an alternative that is built on https://kotlinlang.org/docs/ksp-overview.html[Kotlin Symbol Processing] (KSP) and that processes Kotlin sources directly.

The symbol processor only adapts the symbols of KSP to the model that the annotation processor works with.
The metadata itself is generated by the code that the annotation processor relies upon, so both write the same `META-INF/spring-configuration-metadata.json` file for the same types.



[[appendix.configuration-metadata.symbol-processor.configuring]]
== Configuring the Symbol Processor

KSP is applied with its Gradle plugin.
Once the plugin has been applied, declare the symbol processor in the `ksp` configuration, as shown in the following example:

[source,gradle]
----
plugins {
	id "com.google.devtools.ksp" version "$kspVersion"
}

dependencies {
	ksp "org.springframework.boot:spring-boot-configuration-symbol-processor"
}
----



[[appendix.configuration-metadata.symbol-processor.mixed-modules]]
== Modules That Contain Java and Kotlin

KSP also processes the Java sources of a module, so the symbol processor describes the configuration properties that are declared in Java as well.
Both processors write `META-INF/spring-configuration-metadata.json`, so a module that applies both fails to build with a duplicate entry for that file.
Apply only one of them to a module.



[[appendix.configuration-metadata.symbol-processor.kotlin]]
== How Kotlin Types Are Described

A Kotlin class is described the way that Java sees it:

* A property is bound using its getter and its setter, so a `var` is a property and a `val` is one only when its type is a `Collection` or a `Map`.
* A class whose only constructor has parameters is bound using that constructor.
When a parameter has a default value, the metadata has no default value for the property unless it is annotated with javadoc:org.springframework.boot.context.properties.bind.DefaultValue[format=annotation].
* Types are reported using their JVM names, so a `List<String>` property is described as `java.util.List<java.lang.String>` and an `Int` property is described as `java.lang.Integer`.
* The description of a property is taken from its KDoc, or from the matching `@property` or `@param` tag of the KDoc of the class when it is declared in the primary constructor.
* A property that is annotated with `@Deprecated` is deprecated.
* A nullable parameter of a javadoc:org.springframework.boot.actuate.endpoint.annotation.ReadOperation[format=annotation] method is optional.



[[appendix.configuration-metadata.symbol-processor.additional-metadata]]
== Adding Additional Metadata

The metadata of `META-INF/additional-spring-configuration-metadata.json` is merged into the generated file, which also removes the properties that the additional metadata ignores.
As KSP gives a processor no access to the resources of the module, the directories to look into have to be listed with a processor option, as shown in the following example:

[source,gradle]
----
ksp {
	arg("org.springframework.boot.configurationprocessor.additionalMetadataLocations", "src/main/resources")
}
----



[[appendix.configuration-metadata.symbol-processor.limitations]]
== Limitations

The symbol processor does not support the following features of the annotation processor:

* Default values that are declared with an initializer, such as `var port: Int = 8080`.
KSP does not give a processor access to initializers, so annotate the property with javadoc:org.springframework.boot.context.properties.bind.DefaultValue[format=annotation] or describe the default using xref:specification:configuration-metadata/annotation-processor.adoc#appendix.configuration-metadata.annotation-processor.adding-additional-metadata[additional metadata].
* Reusing the metadata of a type of another module that is annotated with javadoc:org.springframework.boot.context.properties.ConfigurationPropertiesSource[format=annotation], as KSP gives a processor no access to the resources of the classpath.
* Lombok, which KSP does not run.
